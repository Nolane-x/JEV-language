## Repair boundary

M14 is a bounded deterministic repair system, not free-form code completion.

A repair candidate may contain only:

- source patches generated by registered repair generators from supplied diagnostic/knowledge context;
- declared PIR graph operations;
- evidence references and expected diagnostic changes.

The Decision Pack may rank only candidate IDs already generated by the deterministic candidate layer. An out-of-set answer is rejected with `REPAIR_RANKER_OUT_OF_SET`. Low-confidence ranking falls back to deterministic cost ordering.

No Jev/provider response is permitted to introduce source text, AST fragments, PIR operations, imports, symbols or arguments that were not already present in the bounded candidate set.

## Diagnostic and source-location behavior

Compiler diagnostics are normalized into a stable repair taxonomy:

- syntax;
- type;
- missing-symbol;
- import;
- argument;
- return;
- nullability;
- test-failure;
- runtime;
- unknown.

Where PIR source bindings exist, diagnostic spans are mapped to overlapping nodes first and nearest nodes second.

Repair generators must not assume that a compiler's diagnostic range is the exact edit range. The T233 return/type generator specifically resolves the return-expression range when the compiler points at the `return` keyword, as observed in the M14 acceptance fixture.

## Compile/test/rollback semantics

For every selected candidate:

1. apply source patches and optional PIR transaction;
2. compile/type-check;
3. reject or retain only evidence-improving states;
4. run targeted tests after compile success;
5. run regression verification before final success;
6. rollback when compile/test evidence does not improve or regression fails.

Budgets cover:

- iterations;
- candidates per iteration;
- compiler runs;
- test runs;
- wall-clock deadline.

Budget exhaustion returns a structured failure and does not silently report success.

## Test normalization

`normalizeRepairTestResult()` turns pass/fail/skipped cases into one stable result schema and creates stable `TEST_CASE_FAILED` repair diagnostics for failing cases.

A passing compile does not substitute for required behavioral or regression evidence.

## Acceptance benchmark

The pre-registered-style deterministic acceptance fixture starts from:

`answer(): number` returning the string `"41"`.

The TypeScript backend reports `TS2322`. The bounded T233 generator produces exactly one configured numeric replacement candidate. The repair loop must then prove:

- repaired source contains `return 41;`;
- compiler/typecheck passes;
- executable target behavior returns numeric `41`;
- unrelated regression behavior `keep() === 7` still passes;
- exactly one candidate is accepted;
- no rollback is required for the successful path.

Separate conformance cases prove:

- non-improving candidates are rolled back;
- compile-budget exhaustion returns structured failure;
- all four required repair-generator families remain bounded/configured;
- diagnostic span → PIR node location works;
- out-of-set Decision Pack answers are rejected;
- low-confidence ranking falls back deterministically.

## Non-claims

M14 does not claim:

- arbitrary open-ended code repair;
- generative source synthesis;
- whole-repository refactoring;
- arbitrary multi-file dependency repair;
- sound repair for every TypeScript/Python diagnostic;
- static proof that a passing bounded test suite implies general correctness.
